# 09 养成系统设计

> 版本：V1.0 方案稿
>
> 适用范围：PRD S4 养成互动（BB-GRW-001），涵盖用户投喂、番茄钟 / 已配置任务、心情值、金币结算，以及硬件与 App 状态反馈。
>
> 关键边界：业务后端是任务、心情值和金币的权威存储及结算端。AI 不决定奖励数额，不改写金币 / 任务结果，不把对话或情绪识别变成结算授权。

## 1. 设计目标与原则

养成反馈用于回应用户明确发起的互动和已配置任务，提供轻量、可理解的进度感；不以高频打卡、连续使用奖励、缺席惩罚或情绪依赖驱动留存。

1. **只对可核验的业务事件结算。** 投喂、番茄钟完成或其他任务完成必须是获准的事件类型，并由后端核验用户、任务条件、事件身份与唯一性。
2. **后端规则决定账目。** 奖励值、数值区间、任务清单、成本 / 奖励公式、初始值与异常补偿由后端提出并评审；客户端和 AI 不自行计算或覆写。
3. **状态分开表达。** 互动收到、任务完成、奖励结算、数值到账和动画播放是不同状态，不能由一段本地动画代替服务端结算回执。
4. **离线不造账。** 断网时养成模块按 PRD 只读 / 不可用降级；不在端侧累加金币、完成任务或发奖。
5. **账目可追溯且幂等。** 每一笔数值变化都能回溯到唯一事件、任务和规则版本；重试、并发、重连或补传不得重复生效。
6. **陪伴不等于刷数值。** AI 对话、情绪标签、倾诉时长和负面情绪不直接触发金币或心情值变化；不给用户制造“多聊才能养好”的压力。

## 2. 核心数值与账目

PRD 明确存在的养成数值为心情值与金币；产品**不设饱食度、EXP**。等级关系、数值范围、初始值、任务清单及消耗 / 奖励公式仍待后端评审，不在本方案中假定为已冻结。

| 对象 | 业务含义 | 建议数据口径 | 变更来源 / 边界 |
| --- | --- | --- | --- |
| 心情值 `mood_value` | 邦布养成界面的游戏状态，不是用户心理状态，也不是 AI 的情绪识别结果 | 建议使用后端配置的有界整数；可评审 `0-100` 作为候选范围，初始值、上下限和每次变化量待确认。到达边界时按后端规则处理，不溢出。 | 仅由已批准的投喂 / 任务规则等业务事件驱动；AI 情绪标签和对话内容不直接改值。 |
| 金币余额 `coin_balance` | 可用于已批准养成 / 商店规则的虚拟账目 | 建议以最小单位存储整数；余额不得由客户端本地推算。初始余额、上限和奖励额待后端确认；消费前校验余额，不足时拒绝，不产生未批准的负余额。 | 完成获准任务时按规则入账；消费须由 App 展示商品 / 价格 / 余额并取得用户明确确认，后端复核后扣减。AI 不扣币、不下单。 |
| 任务状态 `task_status` | 表示任务的真实流程进度，不是经验值 | 建议将任务状态与数值账目分表 / 分域保存；最终状态枚举、开始 / 完成 / 取消条件由后端定义。 | 仅在用户操作及任务规则满足后由后端更新；硬件播放完成动画、AI 说“完成了”均不等于任务已完成。 |
| 成长事件 `growth_event` | 可追踪的互动 / 任务业务事件 | 至少关联唯一 `event_id`、事件类型、对象、发生 / 接收时间、规则版本和处理状态。 | 事件用于校验和结算，不引入未批准的“亲密度”“连续签到积分”等额外数值。 |

### 2.1 账本模型

- **余额为权威结果，流水为审计依据。** 后端可提供当前 `coin_balance` / `mood_value` 快照，同时保存每笔变更的 `delta`、变更前后值、来源事件、规则版本和结算状态。客户端只展示回执，不凭本地历史事件重建权威余额。
- **奖励按配置表结算。** 逻辑表达为 `delta = approved_rule(event_type, task_id, rule_version, validated_conditions)`。当前 PRD 未批准各事件具体奖励值、任务条件、每日上限或投喂频率；规则表上线前须完成后端评审和验收。
- **单次业务事件只产生一次账目结果。** 建议在后端以 `event_id + resource_type + rule_version` 或经后端批准的等效幂等键标识结算。金币和心情值若由同一事件变化，需在一个原子业务事务内写入，避免一个成功、另一个重复或遗漏。
- **更正用冲正 / 补偿记录。** 已入账后发现业务错误时，不由 AI 或客户端直接覆盖余额；由后端按批准规则生成可追溯的冲正 / 补偿流水，并关联原记录及处理原因。
- **查询余额不等于结算成功。** 交易 / 奖励结果未知时，按原 `event_id` 查询权威状态；未核对原状态前不能新建替代事件、重复发奖或展示“已到账”。

## 3. S4 互动触发与结算链路

### 3.1 事件类型与触发边界

| 业务事件 | 用户动作 | 后端校验重点 | 可结算条件 |
| --- | --- | --- | --- |
| `feed_interaction`（投喂互动） | 用户主动在已批准入口投喂邦布 | 用户 / 设备绑定、物品或互动类型是否可用、事件是否重复、适用规则版本 | 仅满足已配置投喂条件时，按后端批准规则改变心情值 / 金币；缺少规则或失败时不发奖。 |
| `pomodoro_completed`（番茄钟完成） | 用户完成已配置番茄钟；App / 后端按权威任务状态产生完成事件 | 任务归属、计时 / 完成状态、取消 / 过期状态、是否已完成 / 已结算、事件唯一性 | 只有符合批准完成条件的完成事件进入任务结算；AI 不判定完成时间、不发奖。 |
| `configured_task_completed`（其他已配置任务完成） | 用户完成后端已配置的任务 | 任务版本、必需步骤、用户权限、有效期和重复事件 | 按任务专属规则结算；未配置任务或条件不满足时不产生奖励。 |

事件必须由用户交互入口或已批准的确定性任务系统产生。AI 回复、情绪标签、语音中的“我完成了”或硬件动作本身不能直接生成奖励事件；如果用户通过语音提出任务意图，AI 只能传递候选意图 / 事件，后端仍须核验真实任务状态。

### 3.2 结算流程图

```text
用户主动投喂 / 完成已配置任务
        ↓ 事件生产方按后端批准契约生成 / 获取 event_id，携带 user_id、device_id、task_id、事件类型
提交业务后端（关联 request_id / trace_id、发生时间、接收时间）
        ↓
后端校验授权、设备绑定、任务规则、有效期、事件唯一性与当前账目状态
        ├─ 无效 / 未完成 / 已取消 / 重复 → 拒绝或返回原事件状态，不发奖
        ├─ 已处理过 → 返回原 task_status、ledger_entry 与余额，不重复执行
        └─ 有效且首次结算 → 确定性规则计算变更量并原子写入任务状态及账目流水
                                      ↓ 后端返回权威 settlement_status 与数值结果
                          App 展示任务实际状态及金币 / 心情值真实变化
                                      ↓ 后端将获准反馈指令发给目标硬件
                          硬件播放与实际结果相符的动画 / 音效并回报播放状态
                                      ↓
                    后端分别保存任务、账目与播放回执，供对账与问题排查
```

**逻辑顺序：**先校验用户 / 设备 / 任务及事件身份，再由后端结算；App 展示实际结果；硬件按获准结果反馈并回传播放回执。具体物理链路 / 协议由 AI、后端、App 和硬件团队确认，但不得更改后端作为账目权威端的边界。

### 3.3 结算与硬件反馈的三条状态线

| 状态线 | 成功含义 | 用户可见反馈 | 不得混同 |
| --- | --- | --- | --- |
| 互动 / 任务线 | 输入已收到、通过条件校验或任务达到真实完成状态 | “互动已收到” / “番茄钟已完成”，文案依后端回执 | 互动已收到不等于任务完成。 |
| 账目结算线 | 后端流水已成功写入，余额 / 心情值结果可查询 | 展示真实变更量、当前权威值；处理中 / 未知时如实提示 | 任务完成不等于奖励到账；客户端推算值不是账目。 |
| 硬件反馈线 | 对应动画 / 音效已由硬件实际播放并回传 | 邦布播放与实际结算结果匹配的动画 / 音效；必要时使用中性确认反馈 | 动画播放成功不代表任务完成或奖励到账；动画失败不撤销已成功结算。 |

收到事件但尚未结算时，只能播放非奖励承诺式确认（若硬件策略允许），例如短暂的“收到”反馈；不得播放代表金币已到账的成功动画或说“你获得了金币”。结算成功后，动画播放失败只记录硬件反馈故障，不重复发奖；结算失败 / 未知时不得显示成功奖励动画。

## 4. App 与硬件一致性

- 后端一次回执至少说明原 `event_id`、任务状态、结算状态、金币 / 心情值实际变更、当前权威余额 / 数值、账目流水标识和规则版本。App 与硬件按同一事件结果渲染，避免分别推算。
- App 以服务端回执更新数值；本地缓存只能标为“上次同步”或“数据可能过期”，不能叠加未确认奖励。若反馈晚到，先查询原事件的当前状态。
- 硬件动画命令与任务 / 账目结算回执使用同一 `event_id` 关联；反馈命令另有 `feedback_id` / `playback_status`，其失败不改变账目状态。
- 设备收到重复 MQTT 消息时可再次确认已有播放结果，但不得重复结算，也不得反复播放易被理解为多次奖励的动画。重复播放策略由硬件 / 交互评审确认。
- 任务完成、奖励到账、动画播放应分别写入状态与时间戳：例如 `task_status=completed`、`settlement_status=settled`、`playback_status=played`。任何缺失都应按对应子状态提示，不使用一个“成功”覆盖全部流程。

## 5. 弱网、断网与防重矩阵

| 情况 | App / 硬件表现 | 后端处理 | 禁止行为 |
| --- | --- | --- | --- |
| 养成模块进入断网状态 | 按 PRD 只读 / 不可用；可展示最后同步数据并明确标注不可操作 / 可能过期 | 暂停新的养成写入和结算，等待服务恢复 | 不允许本地发奖、扣币、完成任务或把动画当成功；不承诺离线养成可用。 |
| 事件提交前网络断开 | 提示功能暂不可用；不创建本地结算结果 | 不产生新账目流水 | 不用断网缓存伪装为已提交或已到账。 |
| 已提交事件但响应超时 / 结果未知 | 显示“正在核对”或“结果暂不可确认”，保留原事件关联 | 恢复后按原 `event_id` 查询 / 对账；返回权威原状态，再决定是否按批准契约完成尚未执行的原结算 | 不生成新的 event_id 重做；不把超时当失败或成功。 |
| 同一事件重复 / 并发上报 | 返回原任务与结算结果 | 后端持久化幂等键和执行控制，最多结算一次；同键不同载荷拒绝 / 报冲突 | 不因 App 连点、MQTT 重投、服务重启或硬件重连重复发奖。 |
| 延迟事件 / 离线补传 | 显示实际同步状态；未确认前不展示新奖励 | 按授权用户、事件身份、任务、时间、目标和当前状态核验；补传仅补记录、不重复结算。PRD 10.2.10 提到恢复联网后对账补结算，具体允许补结算的事件条件须由后端定义；如批准对原未结算事件补结算，也必须沿用原身份且只结算一次。 | 不将历史补传当作新的任务 / 奖励触发，不重复发币；不重放旧控制事件。 |
| 条件不满足 / 任务取消或过期 | 显示任务的真实状态及未获奖励原因 | 拒绝结算或按已批准规则返回实际结果 | 不以硬件动画、AI 回复或用户重复提交覆盖判定。 |
| 结算成功但 App / 硬件状态滞后 | App 查询原事件后刷新权威值；硬件缺回执时标记播放未知 / 失败 | 保持已结算流水，分别补齐展示同步和播放状态 | 不为补 UI 或重播动画再结算一次。 |
| 登录用户 / 绑定设备 / 任务目标不一致 | 显示权限或设备状态错误 | 拒绝操作；校验身份、当前绑定与目标版本 | 不将旧设备事件作用于新设备或其他用户。 |
| 服务端结果未知 | 保留“处理中 / 结果未知” | 查询 / 对账原业务操作，向用户返回最新权威状态及更新时间 / 版本 | 不把“请求已收到”当作结算成功，不创建替代请求。 |

**恢复流程：**联网恢复 → 校验身份、绑定关系、目标设备与规则版本 → 查询原 `event_id` 和实际任务 / 账目状态 → 去重补传获准记录 → 仅按后端批准的结算契约处理原未结算事件 → 同步真实结果 → 恢复新请求。补传不重复结算，不重放已完成奖励。

## 6. 与情感陪伴和低频互动的融合

### 6.1 V1.0 默认边界

- **AI 对话不直接改变游戏数值。** 对话轮数、持续时长、正 / 负情绪标签、AI 识别的异常信号、用户披露的私密内容均不作为金币 / 心情值的自动奖励依据。V1.0 默认不设“多聊多得”或负面情绪换奖励。
- **明确任务才产生游戏结果。** 用户投喂、完成番茄钟等 S4 互动可按已批准规则产生变化；是否奖励、奖励多少由后端规则表决定，而不是由模型自由决定。
- **心情值不是心理测量。** 养成界面的 `mood_value` 是游戏状态，不等于 PRD 情绪标签、情绪曲线或用户真实心理状况；两者分域存储，不互相推导、不以临床语言呈现。
- **低频存在不要求签到。** 邦布可用预设表情 / 灯效提供低频反馈；未使用、跳过任务、停止对话或休息不会扣值、失去奖励、触发挽留或被标为关系疏远。
- **避免刷数值和情感操纵。** 不以连续互动、连续天数、限时损失、虚拟关系或稀缺奖励迫使用户回来；任务节奏可由用户控制。若未来加入每日上限、冷却或重复投喂限制，需有明确产品目的并经后端 / 安全评审，不预设未批准阈值。

### 6.2 后续若考虑对话相关奖励

当前不启用。若未来提出，须作为独立功能评审，至少满足：奖励与明确、可核验且用户主动接受的离线游戏任务绑定，不按消息数量 / 时长 / 情绪强度计奖；不把倾诉、风险披露、AI 情绪推断或依赖表达转成奖励条件；有频率上限、退出方式和反操纵评估；由后端规则结算并保持账目幂等。未经批准不得上线或用 Prompt 变相实现。

## 7. 核心数据字段建议

字段名称、枚举、幂等域、保留期和接口形式待后端评审；本表只给出逻辑数据契约。

| 对象 / 字段 | 类型 / 说明 | 约束 |
| --- | --- | --- |
| `event_id` | string；一次用户互动 / 任务完成事件的稳定身份 | 同一事件重试、补传沿用原值；生成规则和唯一作用域由后端定义。 |
| `request_id`, `trace_id` | string；请求与跨组件链路关联 | 串联输入、业务校验、结算回执、动画 / 音效回执。 |
| `user_id`, `device_id`, `binding_version` | string；授权用户、目标设备与当前绑定版本 | 后端验证绑定关系，不信任客户端自报身份；切换设备时旧目标失效。 |
| `event_type`, `task_id`, `task_version` | enum / string；事件种类、任务和任务定义版本 | 只接收已批准类型；来源于 AI 的意图不是完成事件。 |
| `occurred_at`, `received_at` | ISO 8601；发生时间与服务端接收时间 | 毫秒精度、显式时区；服务端时间用于对账 / 去重，设备时间作为参考。 |
| `event_status` | enum；例如 received / validating / accepted / rejected / unknown | 最终枚举由后端确定；收到事件不等于接受或结算。 |
| `task_status` | enum；实际任务进度 | 由后端任务规则更新；不以动画播放结果更新任务状态。 |
| `settlement_status` | enum；例如 not_started / processing / settled / rejected / unknown | 仅后端返回权威值；状态未知时先查询原事件。 |
| `rule_id`, `rule_version` | string；使用的后端结算规则 | 支持审计和复现；规则变化不追溯改写既有账目。 |
| `ledger_entry_id` | string；一条金币 / 心情值流水标识 | 唯一、不可因接口重试重复入账；冲正需关联原流水。 |
| `resource_type`, `delta`, `balance_before`, `balance_after` | enum / integer；金币或心情值及变更前后值 | 具体单位、范围、精度及上下限须后端批准；客户端不得计算权威余额。 |
| `playback_feedback_id`, `animation_id`, `playback_status` | string / enum；硬件反馈指令与实际播放状态 | 与账目状态分离；播放失败不触发奖励重结算。 |
| `error_code`, `error_detail` | string / null；失败、冲突、未知原因 | 保留排障必要信息，不写入通用日志中的敏感对话内容。 |

## 8. 异常处理与验收

| 验收场景 | 通过标准 |
| --- | --- |
| 投喂 / 番茄钟完成 | 事件身份唯一；后端按已批准规则结算；App 显示真实变化；硬件反馈与同一业务结果对应。 |
| 任务条件不满足 | 任务和余额不被改写；硬件 / App 不呈现已获奖励。 |
| 请求超时 / 回执丢失 | 可按原 `event_id` 查询实际状态；不重复结算，不误报成功或失败。 |
| 重复、并发、服务重启后重试 | 相同操作只产生一次任务变更和奖励流水；同键异载荷被拒绝或明确报冲突。 |
| 弱网 / 断网 | 养成模块只读 / 不可用；没有本地发奖或伪造结算；重连后核验原事件、身份、绑定和实际状态。 |
| 延迟补传 | 事件去重；补传仅补记录、不重复结算；任何补结算都必须是后端批准的原事件一次性对账处理。 |
| 动画成功但结算失败 / 未知 | 用户不会看到“奖励已到账”；动画不改变任务和账目状态。 |
| 账目结算成功但动画失败 | 账目仍是已结算；播放失败单独记录与排查，不再次发奖。 |
| App / 硬件状态不一致 | 通过服务端回执 / 对账发现并刷新；不可用端侧动画覆盖账目。 |
| AI 说“任务完成”或识别到积极情绪 | 没有有效任务事件和后端结算时，金币 / 心情值不变。 |
