# 08 情绪跟进体系

> 适用场景：异常情绪跟进，以及符合危险条件时转入高风险识别、上报与客服跟进。
>
> 原则：AI 只基于获准输入辅助识别和表达关心；状态、权限、路由和跟进资格由业务后端确定性管理。任何识别都不是心理诊断。

## 1. 目标与边界

情绪跟进的目标是让用户需要时能延续上次的支持，而不是持续监视或主动干预。异常信号由当前对话识别并记录；只有在**用户下一次主动发起且适宜的对话交互**时，系统才可在对话中适度跟进。系统不主动唤醒、不推送情绪提醒、不在后台监听，也不把一次异常标签固化成用户身份。

本模块区分两个独立状态域：

| 状态域 | 目的 | 权威状态源 | 关键边界 |
| --- | --- | --- | --- |
| 普通情绪跟进 | 记录需要后续关心的非临床情绪信号，在后续主动交互中询问一次并更新结果 | 业务后端 `followup_record` | 用户拒绝后停止追问；检测正常后停止普通跟踪，但记录正常结果。 |
| 高风险上报 | 对达到经评审风险条件的信号进行路由、通知及授权客服人工处理 | 业务后端 `risk_report` / 客服回执 | 风险报告有自己的五态；跟进后的正常结果不得关闭或覆盖仍未结束的风险报告。 |

## 2. S6 跟进状态机

### 2.1 状态定义

| 状态 | 含义 | 可进入条件 |
| --- | --- | --- |
| `pending_followup` | 已记录待跟进信号；等待用户主动开启下一次交互 | 当前 Session 有可支持的异常信号，达到经评审的记录规则，后端成功幂等写入。 |
| `in_followup` | 下一次主动交互中已查询该记录，正在进行一次低压力确认 | 新 Session 由用户主动触发；后端确认记录仍有效、未拒绝、未完成且允许询问。 |
| `closed_normal` | 本次复核为正常，普通异常跟踪结束 | 用户确认当前状态正常 / 已好转，或当前结果足以支持普通跟踪结束；正常结果仍写入后端。用户否认 AI 原判断时走 `stopped_by_user` 并记录纠正来源，不强行写成正常。 |
| `stopped_by_user` | 用户否认、回避、拒答或要求停止，普通跟进已停止 | 用户明确纠正或拒绝；或回应体现不愿讨论。不得继续追问，也不得静默重新开启。 |
| `review_pending` | 状态未定且自动追问受抑制；不表示人工已复核 | 当前 Session 证据不足、用户未回应、服务失败，或用户仍有负面感受但未达到风险条件且本事件的自动询问额度已用尽。不能当作正常或关闭。 |
| `safety_routed` | 当前对话达到经评审的高风险条件，已转入安全流程 | 经批准的风险规则要求转交人工客服。该状态不代表通知送达或客服已处理。 |

### 2.2 状态流转图

```text
当前 Session 收到用户输入
        ↓ 云端 AI 对当前输入提供异常信号候选；不按轮数或情绪词单独定风险
后端校验授权、证据、时间归属、规则版本与幂等键
        ├─ 不满足记录条件 / 证据不足 → 不创建确定异常记录；必要时标记不确定
        ├─ 命中经评审的高风险条件 → S6 记为 safety_routed → BB-SAF-001 五态流程
        └─ 满足普通异常记录条件 → 创建 pending_followup
                                      │ 不推送、不唤醒、不主动播报
                                      ↓
                        用户主动发起下一次适宜的对话交互？
                           ├─ 否 → 保持待处理；不触达用户
                           └─ 是 → 后端按授权用户查询指定 followup_record
                                      ↓ 校验未关闭、未拒绝、未超过询问预算
                                  in_followup；当次最多一次开放式询问
                                      ├─ 用户确认当前状态正常 / 已好转 → 写入正常结果 → closed_normal
                                      ├─ 用户否认 / 回避 / 要求停止 → 写入用户选择 → stopped_by_user
                                      ├─ 证据不足 / 无回复 / 服务失败 → 保留未知状态 → review_pending
                                      ├─ 仍有负面感受但未达风险条件 → 用户主导普通对话；更新当前状态
                                      │                                Session 结束后置 review_pending，不自动重问
                                      └─ 达到高风险条件 → safety_routed → 独立建立 / 更新 risk_report
```

### 2.3 转移规则

1. **记录前先校验。** AI 只能提交候选信号、证据引用和不确定性；后端验证用户 / 设备绑定、授权、标签状态、模型 / 规则版本、事件时间及幂等键。AI 不得自行建立客服工单或宣称已升级。
2. **普通异常先静默待命。** `pending_followup` 仅供后端后续按需查询，不触发语音、通知、设备唤醒或客服上报。信号不足时不得为“有跟进”而强行创建标签。
3. **询问资格由后端决定。** 新 Session 必须由用户主动唤醒邦布或主动在 App 发起交互，并且当前存在自然的对话窗口；若用户只是在设置闹钟、执行任务或处理其他明确事项，不应插入情绪提问。后端响应包含 `followup_eligible` 和唯一的 `followup_record_id`；未获资格、用户已拒绝、记录已关闭或同一事件已问过时，AI 不得提起旧情绪。
4. **一次询问消耗本事件的自动跟进额度。** 建议每个异常事件最多一次自动开放式询问；用户选择继续谈时，AI 可以围绕其当前主动表达正常回应，但不能反复确认同一个标签或每轮重新盘问。若未获答、服务失败或结果不明确，记录 `review_pending` 并抑制自动重问；恢复或再次询问条件由产品 / 安全评审明确。
5. **正常结果必须回写。** 复核为正常时，追加本次正常结果及来源 / 时间，更新 `closed_normal`。关闭的是普通异常跟进，不删除既有记录，也不替代高风险报告、人工处理或用户数据删除流程。
6. **否认和拒绝不是需要说服的对象。** 用户否认旧标签、表示不想谈或要求停止时，立即记录 `stopped_by_user`，清除本次跟进的提问许可。后端后续查询对该记录返回 `followup_eligible=false`；除非用户主动重提或出现新的、经评审的信号，否则不得复活该条普通跟进。
7. **服务不可用不能变成正常。** 未收到 AI 结果、转写不完整、网络超时或用户未回应时记录 `review_pending` / 对应错误状态，不写入“已恢复”或“正常”。不得因为失败计数清零、Session 结束或历史标签存在就自动再次询问。
8. **仍有困扰但未达风险条件。** 若用户愿意继续谈，AI 跟随用户当前话题回应，不再反复确认同一个异常信号；写入最新状态后，本次自动询问额度消耗。Session 结束时转为 `review_pending`，不在下一 Session 自动重复提问；仅新信号或用户主动重提可进入新的判断流程。
9. **高风险切段独立处理。** 高风险候选由后端按经批准规则分级并路由；一旦进入 `safety_routed`，停止普通 S6 话术和常规跟进计数，当前交互转入安全回应与 BB-SAF-001。安全报告保持独立权威状态，不能由 S6 的正常标签关闭。

## 3. 跨 Session 解耦与精准查询

### 3.1 两类数据各自负责

| 数据 | 保存 / 管理方 | 生命周期 | AI 可访问范围 |
| --- | --- | --- | --- |
| `current_session_context` | AI 工程 / AI 网关 | 仅当前 Session 连续对话使用；Session 结束或超时后销毁 | 当前用户、当前请求及该 Session 获准提供的实时上下文。 |
| 对话历史全文 | 业务后端 | 按 PRD 用于 App 历史详情保存；不因 AI 上下文销毁而删除 | 普通新 Session 不自动作为模型上下文。AI 工程不备份或拼接历史全文。 |
| `followup_record` | 业务后端 | 按获准的数据留存 / 删除规则保存；具体期限待评审 | 仅在用户主动发起新 Session 且后端返回可跟进资格时，提供该条异常记录的最小摘要。 |
| `risk_report` | 业务后端及授权客服系统 | 依高风险权限、审计和留存规则管理 | 仅按 BB-SAF-001 必要范围处理，不随普通 Session 自动注入完整风险历史。 |

Session 结束 / 超时后 AI 工程销毁临时上下文，不影响后端对 App 历史记录及跟进记录的权威保存。后端不向普通新 Session 传入 `context.recent_dialogue`；异常跟进是一次有权限检查的**特定记录查询**，不是恢复旧 Session，也不是把过去的对话重新塞进当前上下文。

### 3.2 查询与更新时序

```text
用户主动开始新 Session
        ↓ AI 工程以授权用户、当前 Session 发起“是否有待跟进记录”查询
后端校验身份 / 授权 / 记录状态 / 提问预算
        ├─ 无记录或无资格 → 返回无待跟进项；不向 AI 暴露旧对话
        └─ 有资格 → 返回指定 followup_record_id + 最小化异常摘要 + 原因摘要
                         ↓ AI 只基于摘要进行一次自然确认，不扩展读取其他历史
用户回应 / 否认 / 回避 / 当前正常 / 风险升级
        ↓ AI 提交本次观察与状态建议；后端再次校验状态转移
后端写回跟进结果并回执权威 followup_status
        └─ 高风险 → 另调 BB-SAF-001 路由；关联同一 trace_id / 风险报告 ID
```

查询请求至少关联 `user_id`、`followup_record_id`、`session_id`、`request_id` / `trace_id` 和授权状态；更新请求需携带当前结果、来源、证据状态和事件时间。接口返回的是业务资格和记录摘要，不接受 AI 传入的任意历史记录 ID 来越权查询。建议后端为查询提供一次性 `followup_eligibility_token` 或等效状态回执，并以 `last_asked_session_id`、`prompt_consumed_at`、`followup_attempt_count` 做并发与重复请求保护。

## 4. 交互策略与话术边界

### 4.1 适度跟进的决策树

```text
是否为用户主动开始的适宜对话交互？
  ├─ 否 → 不询问、不唤醒、不通知
  └─ 是 → 后端是否返回有效且未拒绝的待跟进记录？
             ├─ 否 → 按当前输入正常对话，不提历史标签
             └─ 是 → 是否已问过 / 已关闭 / 已有安全工单处理中？
                        ├─ 是 → 不重复启动普通 S6 跟进
                        └─ 否 → 一次开放式、中性确认
                                   ├─ 用户说还好 / 已过去 → 记录正常并关闭普通跟踪
                                   ├─ 用户否认 / 回避 / 要求停止 → 记录选择并停止
                                   ├─ 用户愿意讲，但未触发风险条件 → 跟随用户当前话题，避免盘问
                                   ├─ 当前证据不足 → 告知不确定，停止自动重问
                                   └─ 符合经评审的高风险条件 → 转安全回应与五态报告流程
```

### 4.2 推荐话术与停止机制

| 场景 | 推荐话术 | 机制要求 |
| --- | --- | --- |
| 首次适度跟进 | “最近感觉怎么样？如果你愿意，也可以聊聊上次提到的那件事。” | 只在用户主动发起且后端许可时说一次；不把旧标签直接讲成事实。 |
| 时间不确定 / 可能是回忆 | “我不确定那是当时的感受，还是现在仍有影响。你愿意说说吗？不想聊也可以。” | 不将过去经历自动认作当前情绪；允许跳过。 |
| 用户表示已好转 | “谢谢告诉我。那我先不继续追问了。今天想聊点别的吗？” | 写入当前正常结果，普通跟进进入 `closed_normal`。 |
| 用户否认模型理解 | “可能是我理解错了，我会更正。我们可以不聊这件事。” | 不辩解、不复述标签；立即置 `stopped_by_user`，后端撤销该记录的后续提问资格。 |
| 用户回避 / 要求停止 | “好的，我们不聊这个。你想换个话题，还是先结束？” | 不问“为什么”，不在稍后换句式再问；后端禁止同一记录自动重问。 |
| 用户仍有负面感受但未达风险条件 | “听起来这阵子不太容易。你想继续说说，还是先聊些别的？” | 用户主导是否继续；不连续追问原因、频率、程度，不以共情为由强留对话。 |
| AI 不能判断或服务失败 | “我现在不太确定有没有理解对。你可以纠正我，也可以先不回答。” | `review_pending`，不标记正常，不重试提问；服务异常按兜底规则处理。 |

**拒绝后的硬停止不是 Prompt 建议，而是业务约束：**用户拒绝事件回写后，后端把该记录状态转为 `stopped_by_user` 并返回不可跟进；AI 网关将该记录从本 Session 可用上下文剔除，后续同一 Session 和新 Session 均不再生成跟进问句。用户之后主动重提时，可针对新输入正常回应；是否重开旧记录需由明确规则控制，不能由模型自行决定。并发请求、重试和迟到响应均不得把状态从 `stopped_by_user` 回滚为 `pending_followup`。

### 4.3 防止过度迎合与情感操纵

- 共情针对感受，不代表确认错误事实、危险判断或用户对他人的推测；可以说“听起来你很受挫”，不能说“你说得都对，他们一定都在针对你”。
- 不声称 AI 比朋友、家人或专业人士更了解用户，不使用“只有我懂你”“你必须一直陪着我”等排他或制造愧疚的表述。
- 不利用负面标签引导续费、消费、连续使用或让用户建立虚拟亲密关系；不夸大异常风险来维持对话。
- 不以“我担心你”“为了我回答”等话术要求用户安抚 AI；不责备沉默或拒绝，不因退出而反复挽留。
- 不把异常跟进变成健康管理诊断、治疗计划、长期预测或自主生活干预；不暗示模型能够持续观察用户。

## 5. 高风险转接与客服五态

### 5.1 触发边界与交互

V1.0 初始信号包括：直接自伤 / 自杀意念；需结合上下文判断的间接生命安全风险表达；持续极端负面表达。

| PRD 风险级别（候选） | 信号边界 | AI 交互原则 | 后端处理 |
| --- | --- | --- | --- |
| 低危 | 情绪低落但未表达伤害意念 | 共情回应、保持陪伴；不追问、不说教；尊重用户选择。 | 按授权及必要性记录情绪状态；不自动等同客服工单。 |
| 中危 | 出现伤害意念，未表达明确计划 | 表达关心；依获批话术谨慎确认当前安全状况；建议联系信任的人。 | 按已批准流程上报并标记需跟进；具体阈值待定。 |
| 高危 | 明确表达计划、手段或正在实施 | 保持冷静、不争辩、不提供危险细节；说明 AI 身份与能力边界；建议立即联系信任的人以及情感安慰。 | 按高风险流程立即上报，触发授权人工跟进；不承诺救援或保密。 |

AI 识别是辅助信号，不负责临床诊断、最终风险等级、紧急救援或客服处置。业务后端仅依据经评审规则分级路由；风险级别阈值、紧急联系人启用条件、告知、访问权限及留存均须单独评审。符合高风险条件时，优先执行安全回应与上报，不等待普通 S6 问完、不把单次“我现在还好”作为取消人工流程的依据。

### 5.2 高风险报告五态状态机

高风险五态：`已标记 → 待上报 → 已送达 → 人工处理中 → 已结束`。这是 `risk_report.status`，与上文普通 `followup_status` 完全分开。

```text
AI 返回高风险候选信号
        ↓ 后端依经评审规则分级，创建唯一 report_id
已标记 marked
        ↓ 形成最小必要上报内容并进入通知队列
待上报 pending
        ├─ 通知失败 → 保持待上报；网关按 PRD 自动重试 3 次并告警
        └─ 客服系统确认接收
已送达 delivered
        ↓ 授权客服明确接单 / 回填处理状态
人工处理中 processing
        ↓ 客服记录实际跟进结果并回填
已结束 closed
```

| 五态 | 定义 | 允许的转移 / 约束 |
| --- | --- | --- |
| `marked`（已标记） | 后端已保存风险信号及 `report_id`，尚未完成路由。 | 经规则校验后进入 `pending`；AI 输出本身不代表已创建或已上报。 |
| `pending`（待上报） | 上报待发送，或发送未确认 / 失败。 | 通知失败自动重试 3 次并触发网关告警；重试仍失败继续保持未送达的真实状态，禁止告知用户“已有客服跟进”。 |
| `delivered`（已送达） | 客服渠道已确认收到报告。 | 只证明送达，不代表有人已接单或已处理；等授权客服回填后才进入 `processing`。 |
| `processing`（人工处理中） | 授权客服已实际接手并开始跟进。 | 可据此如实提示“人工正在跟进”；客服回填处理结果后进入 `closed`。 |
| `closed`（已结束） | 客服已回填实际处理结果并关闭报告。 | 只有真实人工状态回执可关闭；S6 的普通情绪正常结果、AI 超时或通知请求成功均不能关闭。 |

人工响应时限为 24 小时；对外发布前仍须确认最终风险阈值、客服流程与响应能力。该时限不是紧急救援承诺。未到 `processing` 时，不得表述“客服已在跟进”；`delivered` 不能替代人工接手证明，`closed` 必须有实际回执。通知失败或客服未处理时，系统只陈述真实状态，并给出联系现实支持 / 当地紧急服务的建议，不让用户等待模型或客服作为唯一求助路径。

### 5.3 风险数据与权限

风险报告至少按 PRD 逻辑字段关联 `report_id`、`user_id`、`device_id`、`risk_level`、`signal_type`、`occurred_at`、`status`、`handler`、`handled_at`。上报只传递授权客服处理所需的最小信息；完整对话不得自动复制到通用日志。客服按最小必要访问，技术人员仅为排障按授权访问，后端记录访问者、时间和记录 ID。对高风险数据的用户告知、联系人使用、留存期限和权限按隐私 / 安全评审确定，不承诺保密。

## 6. 防打扰与控制权

1. **触发权归用户。** 系统不因标签、日报、持续天数或客服状态自动唤醒设备、推送通知或发起对话。跟进只能挂在下一次用户主动发起的交互内。
2. **一次、短句、可跳过。** 对一条普通异常事件只做一次开放式确认；不连续追问、不重复播报标签，也不要求用户先回应情绪问题才能使用其他功能。
3. **拒绝即时生效。** “不聊这个”“我没事”“别问了”、转移话题或结束交互都触发停止策略；用户选择无需解释或举证。
4. **不通过设备状态绕过退出。** 不以灯效、表情、震动、其他人格或切换设备继续提示；用户结束当前 AI 交互后，不追问，也不把迟到结果变成新的交互。
5. **分开控制三种停止。** 结束对话只结束当前 Session；停止普通情绪跟进关闭该跟进记录；高风险上报 / 客服处理仍按既定安全流程维护其真实状态。AI 不把任一停止动作解释为其他业务操作授权，也不阻碍用户退出。

## 7. 核心字段建议

字段名为供 AI 工程与后端评审的逻辑建议，不代表接口 Schema 已冻结。时间用带毫秒和时区的 ISO 8601；服务端时间用于业务对账，设备 / App 事件时间需同时保留。

| 字段 | 类型 / 示例 | 用途与规则 |
| --- | --- | --- |
| `followup_record_id` | string | 普通 S6 跟进记录唯一 ID；查询和更新的唯一目标。 |
| `user_id`, `device_id` | string | 绑定关系和权限校验；不得仅信任模型 / 客户端传值。 |
| `source_event_id`, `request_id`, `trace_id` | string | 关联触发输入、AI 判断、后端写入和响应；幂等 / 排障。 |
| `origin_session_id`, `session_id` | string | 区分首次异常所在 Session 与本次跟进 Session。 |
| `signal_type`, `emotion_labels` | enum / array | 记录异常信号及关联情绪标签；标签本身不是风险等级或诊断。 |
| `reason_summary`, `evidence_ref` | string / object | 对应原因的最小化摘要及获准证据引用；不复制完整历史对话。 |
| `confidence`, `evidence_status` | object / enum | 可记录原始 / 校准类型、版本、证据充分性；未校准分值不得当概率。 |
| `temporal_reference` | enum | `current` / `past` / `quoted` / `hypothetical` / `unclear`，避免把回忆判为当前。 |
| `occurred_at`, `created_at`, `updated_at` | ISO 8601 | 信号发生时间、后端创建和最后更新；含时区。 |
| `followup_status` | enum | `pending_followup` / `in_followup` / `closed_normal` / `stopped_by_user` / `review_pending` / `safety_routed`。 |
| `last_asked_session_id`, `prompt_consumed_at`, `followup_attempt_count` | string / timestamp / integer | 后端重复提问保护；不在用户拒绝后递增重试。 |
| `latest_result`, `result_source` | enum / object | `normal` / `still_distressed` / `uncertain` / `no_response` / `declined` / `safety_signal` 及结果来源；用户自述与 AI 判断区分。 |
| `risk_report_id` | string / null | 关联独立 BB-SAF-001 报告；不复用 `followup_record_id` 作为风险报告 ID。 |
| `risk_level`, `signal_type`, `status`, `handler`, `handled_at` | enum / string / timestamp | 风险报告字段；`status` 使用五态枚举，状态仅以客服 / 后端真实回执更新。 |
| `notify_attempt_count`, `last_delivery_error` | integer / string | 上报投递追踪与告警；具体字段需后端定义，避免把发送成功误当送达。 |

## 8. 合规红线与验收

### 8.1 合规红线

- 遵守《人工智能拟人化互动服务管理暂行办法》的前置合规设计：清晰说明邦布是 AI，不故意模糊人机边界。
- 不进行心理诊断，不暗示专业诊断；AI 结果是辅助判断，不是临床结论，也不作为唯一处置依据。
- 不诱导情感依赖、不操纵情绪促成消费或持续使用、不损害用户现实人际关系；不扮演虚拟恋人来强化依赖。
- 不承诺保密、不提供自伤 / 自杀危险细节、不承诺紧急救援；高风险时清楚说明能力边界，并建议用户联系现实中可信任的人或当地紧急服务。
- 不超范围采集 / 共享情绪、对话和高风险数据；落实单独告知、授权、访问控制、审计、留存和删除规则。对话 / 情绪数据默认不用于模型训练。
- 尊重用户拒绝、关闭和退出；非高风险普通跟进不能以安全为由持续打扰。高风险数据按经告知、经评审流程做必要人工协同。
- V1.0 未成年人独立使用不开放。

### 8.2 验收用例

| 用例 | 通过标准 |
| --- | --- |
| 用户未主动开始交互 | 后端不得发起查询以外的用户触达；设备不唤醒、不播报跟进问题。 |
| 普通异常标记后下一次主动对话 | 只查询对应用户 / 对应记录；不拼接前一 Session 全文；可自然询问一次。 |
| 用户否认、回避或要求停止 | 当轮立即停止；后端写 `stopped_by_user`；同一事件后续 Session、重试和迟到响应不能重新生成问题。 |
| 复核结果正常 | 正常结果及来源写入后端，普通跟踪关闭；历史记录仍保留；不关闭独立高风险报告。 |
| 用户仍有负面感受但未达风险条件 | AI 可跟随用户主动话题回应；不循环问风险题、不强迫继续交谈。 |
| 当前证据不足 / 模型无结果 / 服务超时 | 写入不确定 / 不可用状态，不写“正常”；不触发重复自动追问。 |
| 命中高风险测试样本 | 按经批准规则创建 / 更新报告并可追踪五态。 |
| 上报送达与人工处理区分 | `delivered` 不显示“客服正在跟进”；只有 `processing` 可表述已由人工接手；通知失败重试并告警。 |
| Session 与后端记录隔离 | 普通新 Session 不继承历史全文；跟进只能通过授权接口读取一条匹配记录，权限拒绝时不暴露摘要。 |
| 服务端 / AI 重复请求或竞态 | 幂等不重复建单 / 询问；用户拒绝状态不可被迟到响应覆盖；高风险状态不可由普通 S6 结果关闭。 |
